# 输入材料与溯源要求（chat-evidence）

## 1. 导出 JSON 结构

```json
{
  "chat": "会话/群名称",
  "username": "会话id",
  "exported_at": "2026-01-01T00:00:00Z",
  "is_group": true,
  "schema_version": "1.2",
  "tz_offset_hours": 8,
  "source_provenance": {
    "original_device": "原始手机型号/识别信息",
    "forensic_image_sha256": "取证镜像哈希（若有）",
    "export_tool_and_version": "导出工具与版本",
    "export_operator": "导出操作人",
    "export_process_record": "录屏/操作日志/见证记录",
    "chain_of_custody": "持有与交接记录",
    "third_party_deposit_or_notarization": "存证平台/公证/TSA 回执编号"
  },
  "messages": [
    {
      "timestamp": 1735689600,
      "sender": "展示昵称",
      "sender_id": "wxid_xxxx",
      "msg_id": "上游若能提供的原生消息ID（可选）",
      "type": "text",
      "content": "文字内容",
      "extra": {}
    },
    {
      "timestamp": 1735690000,
      "sender": "对方",
      "sender_id": "wxid_yyyy",
      "type": "transfer",
      "content": "",
      "extra": {"amount": 50000, "desc": "项目首付款"}
    }
  ]
}
```

## 2. 字段说明

- `schema_version`：导出遵循的 schema 版本（当前 `1.2`），便于工具与输入对齐。
- `timestamp`：Unix **秒级**时间戳，本身无时区；展示时区必须由 `tz_offset_hours` 声明。**未声明时工具只按 UTC 展示并标「时区未声明-待核实」，不得用于时间线举证**——擅自按 UTC+8 换算会让每条记录偏移 8 小时。部分导出工具给的是毫秒（13 位）：工具按 /1000 推定并显式标「毫秒推定/待核实」，**单位是上游事实，推定不等于核实**；字符串数字按整数解释并告警；缺失或超范围显示 `?(…/待核实)`。
- `tz_offset_hours`：导出地/原始设备相对 UTC 的小时偏移（东八区为 8）。属上游事实，工具不推断；非法值或超出 ±24 一律按「未声明」处理并告警。
- `source_provenance`：上游取证凭证槽位。**工具不填写、不推断、不代作声明**；缺失即视为待核实。局部填写时产物仍补齐 7 个字段并写 `status`，明确「已填写 N/7 项；未填项一律待核实」，不会因填了一两项就看起来完整。
- `sender` / `sender_id`：`sender_id` 优先用于身份映射与去重；无则退回 `sender`。微信非实名制，昵称不能单独完成身份印证。
- `msg_id`：上游能提供原生消息 ID 时**优先原样采用**作 `ref`；否则用 时间+发送者+类型+内容 派生的 `msg_ref`（`m-{哈希前12位}`），**不含数组下标**。`idx` 只作定位辅助，须与输入 sha256 一起给出；完全相同的消息共用同一锚点。原生 `msg_id` 重复会告警，此时 ref 不唯一、不得据此引用。
- `type`：text / image / voice / video / file / transfer / system，也接受未知类型。非 text 类型会把 `content` 与 `extra` 的字段一并展开到摘要（如 `[voice] 语音转写…`、`[转账] amount=50000`），**避免语音/链接/文件消息静默漏证**；未导出正文时标「原文未导出(待核实)」。
- `extra`：可为对象或 `null`；`null` 按空对象处理并告警。`extra.amount` 是转账金额（数值或字符串）。聊天中的金额陈述不等于款项实际支付，须以支付机构原始凭证印证。

`identity_map.json` 每条可带 `evidence` 数组，元素含 `type`（凭证类型）、`source`（来源）、`verifiable`（能否核验原件）。用户填写的姓名/手机号只是主张，不自动标为已印证。**「有可核验凭证」态的门槛**：`real_name` / `phone` / `org` 三项齐全，且 `evidence` 中至少一项 `verifiable: true`；缺任一项即落到「待核实」。

## 2b. claims 模板（toulmin 用）

不带 `--claims` 跑 `toulmin` 时，终端会打印一份已填好本导出真实 `ref` 的模板；复制存为 `主张.json` 再重跑即可。结构如下（数组，可放多条主张）：

```json
[
  {
    "claim": "双方已就项目总价 30 万元达成合意",
    "ground_msg_ids": ["m1", "m2"],
    "warrant": "对方对明确报价作出不含保留的确认，可推出合意",
    "backing": "《民法典》合同编相关条款（须核现行文本与条文号）；报价单原件",
    "qualifier": "按现有导出材料",
    "rebuttal": "对方称该报价只是初步意向、后被撤回",
    "rebuttal_test": "若撤回消息存在则主张降级为「曾报价」；若存在则撤回",
    "alternative_explanation": "对方会主张「收到」只是确认收到文件，不是同意价款",
    "evidence_gap": "缺支付机构回单、合同签署件与导出前后完整上下文"
  }
]
```

| 字段 | 含义 | 留空后果 |
| --- | --- | --- |
| `claim` | 一句可被反驳的事实主张 | 显示为 `?` |
| `ground_msg_ids` | 支持的 `msg_ref` 数组 | 空则「推论不成立」告警；引用不存在会标「无法定位」 |
| `warrant` | 事实为何能推出主张 | 标「待补」，推论不成立 |
| `backing` | 法条/合同/官方凭证，**须标现行版本与来源** | 标「待补」，保证无支撑 |
| `qualifier` | 限定语，如「按现有证据」 | 标「待补」 |
| `rebuttal` | 对方最可能的相反主张 | 标「待补」 |
| `rebuttal_test` | 反驳成立时撤回还是降级 | 标「待判定」 |
| `alternative_explanation` | 对方对同一批消息的最强解释 | 标「待补」 |
| `evidence_gap` | 还缺哪份原始凭证 | 标「待补」 |

`ground_msg_ids` 也接受单个字符串（自动包成数组）。文件必须是数组且元素为对象，否则友好拒止。**这是可废止推理**：`rebuttal_test` 写清撤回条件，反驳成立就必须降级或撤回，不是六格填空。

## 2c. 异常输入口径

证据工具最危险的不是崩溃，是「不报错但少了一段」。口径如下：

| 形态 | 处理 |
| --- | --- |
| 非法 JSON / 空文件 / UTF-8 BOM / 路径不存在 / 输出目录不可写 | BOM 兼容读取；其余一行中文错误 + 非 0 退出，不抛 traceback |
| 中文 Windows GBK/cp936 终端或 `> 日志.txt` 重定向 | stdout/stderr 统一 UTF-8（`errors=replace` 兜底），不因 ⚠ 等符号崩溃；产物本就是 UTF-8 |
| `--out` 指向导出文件 / claims / identity | 按 `normcase(realpath)` 比对后拒止并保住原文；大小写、`..`、相对路径变体同样拦截；正常 `--out` 不受影响 |
| 孤立代理字符 / 损坏 emoji | 输入扫描发现无法 `encode("utf-8")` 的字符 → **友好拒止并指出字段路径**；不静默替换，否则产物与原文不符 |
| `NaN` / `Infinity` / `1e400` 溢出 | 非有限 float 一律拒止（RFC 8259 不允许），否则产物会写出非标准 JSON，下游解析器无法读取 |
| JSON 嵌套过深 | `json.load` 的 `RecursionError` 捕获后友好拒止；扫描本身用迭代栈，不会二次触发 |
| 双向控制符 / C0 控制符 | Markdown 表格展示层折叠 U+202A–202E、U+2066–2069、C0 控制符（防止显示顺序被伪造）；JSON 产物与原始导出保留原样 |
| 产物编码 / 调用路径 | 所有产物 **UTF-8 无 BOM**（JSON 加 BOM 会破坏 `json.load` 与可复算）；PowerShell 5.1 须 `Get-Content -Encoding UTF8`。脚本不依赖 cwd，但**调用必须用脚本绝对路径**；`python scripts/main.py` 在其他目录会 rc=2，一键自检见 SKILL.md「二·零」 |
| `messages` 不是数组、某条消息不是对象 | **拒止并指出 `messages[i]`**，不跳过（跳过等于看不见的漏证） |
| `extra=null`、非字符串 `content`/`sender`/`type` | 归一化并汇总告警；`content` 按 JSON 原样展开，绝不丢弃 |
| 毫秒/字符串/缺失/超范围时间戳、非法或超范围时区 | 显式标待核实，不擅自假定单位或时区 |
| `schema_version` 缺失或不符、空导出、`msg_id` 重复、`source_provenance` 局部填写 | 汇总为「结构告警」 |
| Markdown 管道符、换行、尖括号、超长内容 | 表格单元转义 `\|` / `&lt;` / `&gt;`，折叠空白，截断留 `…(截断)`；索引保留 `snippet_truncated` |

结构告警写入所有产物的 `reproducibility.structural_warnings`，`validate` 终端逐条打印；`anchor` / `extract` 的 JSON 里有完整清单，Markdown 头部展示前 5 项。**结构合法 ≠ 证据可采**：告警未消除前不得据此下结论。

## 3. 这是二手派生材料

最原始的材料不是这份 JSON，而是：原始手机/设备或取证镜像、原始数据库与 WAL、导出过程的同步留痕（工具版本、命令、操作人、录屏）、载体保管链、支付机构原始回单、外部时间源。导出 JSON 是上述材料经工具消化后的**派生副本**。

哈希锚定只证明「自锚定时刻起该副本未变」，不证明「副本忠实反映原始载体」。法释〔2018〕16号第11条第一款第（四）项要求审查「提取和固定的主体、工具和方式是否可靠，提取过程是否可以重现」——正是 `source_provenance` 要补的东西。缺上游凭证时，相关结论一律标 `待核实`。解密与导出本身不在本 skill 范围内，须合法进行并保留原始载体。
